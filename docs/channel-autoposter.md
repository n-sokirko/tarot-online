# Автопостинг в канал @tarro_bot_group

Посты в канал пишутся моделью заново на каждый запуск. До 18.09.2026 это была
ротация примерно 28 написанных вручную текстов (`marketing/autopost.py`), и
счётчик в её state-файле стоял на `n: 83` — то есть подписчики видели каждый
пост по три раза.

## Как устроено

| Что | Где |
|---|---|
| Генерация и защита от повторов | `backend/apps/telegram_bot/channel.py` |
| Запуск | `manage.py post_to_channel` |
| История постов | модель `ChannelPost`, она же в админке (только чтение) |
| Расписание | Railway cron-сервис `cron-channel-post`, `0 6,11,17 * * *` UTC |

06:00 / 11:00 / 17:00 UTC — это 09:00 / 14:00 / 20:00 по Минску, те же слоты,
что были у планировщика Windows.

Ротация: два факта, потом промо. Считается по числу **опубликованных** записей,
поэтому сорвавшаяся отправка не сбивает пропорцию.

## Почему посты не повторяются

Двумя независимыми способами — одного мало:

1. **Список запретных тем.** Темы последних 60 постов уходят в промпт как
   «это уже было, не повторяй». Ловит очевидное.
2. **Отпечаток текста.** `channel.fingerprint()` берёт значимые слова (без
   стоп-слов и без сквозной лексики вроде «карта», «аркан», «колода»), обрезает
   их до 5 символов вместо морфологии и хеширует. `channel.similarity()` считает
   коэффициент Жаккара к 120 последним постам. Выше 0.5 — считаем, что это тот
   же пост, и генерируем заново, до 4 попыток.

Второй слой нужен именно потому, что модель охотно придумывает новую формулировку
темы для старой мысли — список запретных тем такое пропускает. Проверка стоит и
на сервере, в `/api/v1/channel/publish/`, так что ручная публикация мимо неё не
пройдёт.

Если за 4 попытки не вышло ничего нового — команда падает с ошибкой. Пропуск
слота лучше повтора.

## Ручной прогон

```bash
python manage.py post_to_channel --dry-run
```

Печатает пост и ничего не отправляет; в базу тоже не пишет, так что тема не
«сгорает». Без флага — генерирует, публикует и записывает. `--kind promo` или
`--kind fact` перебивает ротацию, `--angle` — угол подачи.

## Редполитика

Голос канала, требования к фактам и формат лежат в `channel.py` (`_SYSTEM`,
`_PROMO_EXTRA`, `_FACT_EXTRA`) и список углов подачи — в `ANGLES`. Это и есть
место, где надо править тон: всё остальное его только передаёт.

Отдаётся наружу как поле `guidelines` в `/api/v1/channel/brief/`.

## Почему это не Claude Code routine

Изначально задумывалось иначе: облачный routine Claude Code ходит в API,
пишет пост сам и публикует его. Это не работает — **egress-прокси песочницы
отклоняет CONNECT** ко всему за пределами своего белого списка (`api.anthropic.com`,
npm, pypi и подобное). Запрос к `web-production-af39f.up.railway.app` возвращает
`connect_rejected (organization policy)`, до нашего API дело не доходит вовсе;
`api.telegram.org` заблокирован по той же причине.

Routine `Tarot channel autoposter` (`trig_0144tMoWo7XNs4vikMGsRNSD`) создан и
**выключен**. Если сетевую политику окружения когда-нибудь получится расширить —
включить его, и он заработает через те же два эндпоинта:

- `GET /api/v1/channel/brief/` — редполитика, тип поста, угол, список занятых тем;
- `POST /api/v1/channel/publish/` — `{topic, text, kind}`; 201 — опубликовано,
  409 — слишком похоже (в ответе `conflicts_with`).

Оба закрыты заголовком `X-Channel-Token` (переменная `CHANNEL_POST_TOKEN`) и при
незаданном токене отказывают во всём.

## Старый планировщик Windows

Задачи `TarotAutoPost_Morning` / `_Afternoon` / `_Evening` на домашнем ПК
**всё ещё включены** и продолжат постить из старого пула — их надо выключить,
иначе в канал пойдут два потока. Нужны права администратора:

```bash
schtasks /change /tn TarotAutoPost_Morning /disable
```

То же для `TarotAutoPost_Afternoon` и `TarotAutoPost_Evening`.

## Стоимость

Три запуска в сутки, на запрос уходит меньше тысячи токенов вывода. Контейнер
крона живёт секунды. На фоне остального счёта Railway это незаметно.
